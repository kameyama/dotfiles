---
name: check-secrets
description: dotfiles に入るシークレットと会社の情報を検査する。commit 前、push 前、PCの既存設定をリポジトリへ取り込むとき、hook に commit / push を止められたとき、「セキュリティチェック」「機密チェック」と言われたときに使う。
---

このリポジトリは PUBLIC で、会社PCでも使う。入れてよいものの基準は CLAUDE.md の「セキュリティ」にある。この検査はその基準に照らして、**commit・push される予定のものを1つ残らず**確かめる。

## 手順

1. **機械的な検査**: 対象に合わせて `bash .claude/hooks/check-secrets.sh <mode>` を実行する。
   - `changes`: commit 前（未 commit の変更と `user.email`）
   - `outgoing`: push 前（リモートにないコミットの中身・メッセージ・作者・コミッター）
   - `all`: 履歴全体の監査（頼まれたときと、パターンを足したとき）

   見つかったものは先頭4文字の伏せ字で表示される。どこにあるかは `git diff HEAD` や `git log -p` を同じ語で絞り込んで探す。
2. **目で読む検査**: パターンは既知の語しか捕まえない。差分（`git diff HEAD`、push 前なら `git log -p --branches --not --remotes`）と commit メッセージを全行読み、パターンにない会社の情報を探す。社名、顧客名、案件名、人名、社内のホスト名・URL・アカウントID、業務リポジトリのパスなど。判断できない行は会社の情報として扱う。
3. **作者**: `git config user.email` が個人用アドレスであることを確かめる。
4. **報告**: 見つかったものと場所をユーザーに伝え、commit・push はユーザーの判断を待つ。会社の情報がパターンにない語だったなら、`~/.config/dotfiles/deny-patterns` に1行足すことを提案する。値そのものはチャットに書かず、場所（ファイルと行、コミット）で示す。

全行を読み終え、手順1〜3のどれにも見つからなかったら完了。その旨を一言で報告する。

## deny-patterns

`~/.config/dotfiles/deny-patterns` は git 管理外。1行1つの拡張正規表現で、大文字小文字は区別しない。`#` で始まる行はコメント。パターン自体が会社の情報なので、リポジトリには入れない。ファイルがないと検査は失敗する（個人PCでは空ファイルでよい）。
